# AI(Gemini) 프롬프트 엔지니어링 및 오류 극복 사례 (AI Usage & Retrospective)

본 프로젝트에서는 AI를 '완벽한 정답 생성기'로 신뢰하지 않고, **충돌 해소를 위한 보조 중재자(Mediator)**로 제한적으로 활용했습니다. 아래는 프로젝트 수행 과정에서 AI와 상호작용한 단계별 기록과 오류 극복 사례입니다.

## 1. 단계별 AI 프롬프트 설계 및 질문 목적

- **Phase 1 (도메인 이해 및 설계 제안)**
  - **질문 목적**: 대체투자 심사역들이 실제로 어떤 기준으로 데이터를 검증하는지 파악하고, 이를 시스템 아키텍처에 어떻게 반영할지 자문을 구함.
  - **AI의 답변**: "결정론적인 Rule과 모호함을 판단하는 AI를 분리하라"는 조언 획득. 이를 바탕으로 `DataNormalizer` -> `GeminiAIService` -> `RuleEngine` 으로 이어지는 3단계 파이프라인이 도출됨.
- **Phase 2 (데이터 합성기 제작 및 프롬프트 제어)**
  - **질문 목적**: `hasConflict=true` 상태로 넘어온 모순된 두 문서를 AI가 비교하여 적절한 값을 추론해 내도록 System Prompt를 튜닝.
  - **AI의 답변**: 초기에는 단순히 AI가 "A문서의 70%가 맞다"고만 응답함. 이를 보완하기 위해 "반드시 원문의 인용구(Quote)를 포함하라"는 강제 제약을 프롬프트에 추가.

## 2. 채택, 수정, 폐기된 AI 제안

- **[채택] Traceable Field 모델 도입**: 데이터의 단순 변수 할당 방식의 한계를 극복하기 위해 제안받은 이력(Lineage) 추적 래퍼 클래스 설계안을 전면 채택하여 `TraceableField<T>` 코어 구현.
- **[수정] 완전 자율형 AI 심사 배제**: AI가 스스로 최종 승인(Approval) 권한을 가지도록 하자는 제안은, 금융 도메인의 보수성을 고려하여 **수정 채택**. AI는 값의 모순만 해소(`PENDING` 상태로 전환)하고, 최종 판정은 반드시 '결정론적인 하드코드 Rule Engine'이 수행하도록 책임을 분리함.
- **[폐기] 외부 문서 직접 파싱 (OCR)**: Python을 이용한 물리적 PDF/Excel 텍스트 스크래퍼(Scraper) 구현 제안은, 과제의 본질인 "데이터의 불확실성 통제 모델 설계"에서 시선이 분산될 우려가 있어 **전면 폐기**하고 가상 데이터 합성기(`DataGenerator`) 방식으로 선회.

## 3. 프롬프트 및 AI 응답 검증법 (Validation)

- **인용구(Quote) 교차 검증**: AI가 반환한 "이유(Reason)" 텍스트 안에 포함된 인용구가 실제 원시 문서(RawDocument) 텍스트 안에 `substring`으로 완벽히 일치하게 존재하는지 검사합니다.
- **Rule Engine 이중 검증**: AI가 모순을 해소하여 LTV 값을 75%로 보정했다 하더라도, 다음 단계인 Rule Engine의 임계치(예: 상한 70%)를 넘으면 가차 없이 `REJECTED` 처리되도록 하여 AI의 독단적 오판을 시스템이 방어(Defense)합니다.

## 4. AI 환각(Hallucination) 및 논리 오류 발견 사례

프로젝트 진행 중 AI가 명백한 논리적 오류나 환각을 일으킨 사례와 이를 제어한 방법입니다.

### 🚫 사례 1: 없는 리스크를 지어내는 환각 (Hallucination)
- **오류 상황**: 환경 리스크가 문서에 전혀 언급되지 않았음에도, AI가 "사모대출 펀드의 일반적인 ESG 정책에 따라 환경 리스크가 존재할 수 있다"며 임의로 위험 요소(Risk)를 생성하여 반환함.
- **극복 방법 (SC-04 반영)**: 프롬프트에 *"Do not assume any risk that is not explicitly stated in the provided text. If you find a risk, you MUST return the exact matching quote."* 라는 엄격한 제약을 추가하고, 인용구 검증 로직을 시스템에 탑재하여 원문에 없는 근거는 `confidence` 점수를 0으로 강등시킴.

### 🚫 사례 2: 단위(Unit) 변환 논리 오류
- **오류 상황**: IM 텍스트에는 "요청 금액: 50억원", 이메일 텍스트에는 "요청 금액: 50,000,000,000원(5백억)" 이라고 정상 기재되었으나, AI가 둘의 숫자가 다르다며 `Conflict`를 선언함.
- **극복 방법 (SC-02 반영)**: 수치 데이터의 스케일(Scale)을 정규화하는 작업은 AI에게 맡기면 안 된다는 것을 깨달음. 따라서 금액이나 환율의 단위 정규화(Normalization)는 AI를 호출하기 전 `DataNormalizer`의 결정론적인 Java 코드로 선처리(Pre-processing)하도록 파이프라인의 역할을 강제로 분리함.
