# [과제 C] 대체투자 심사 지원 시스템 프로젝트 설계서 및 요구사항 명세

## PART 1. 시스템 구현 설계 (Architecture & Design)

이 문서는 노아에이티에스(주) 과제 C 요구사항을 바탕으로, 실제 동작하는 시스템을 구현하기 위한 기술 스택, 아키텍처 및 데이터 모델을 상세히 정의한 종합 설계서입니다. 향후 본 문서의 설계 내용은 제출 형식에 맞게 개별 문서(`ARCHITECTURE.md`, `DATA_MODEL.md` 등)로 분리되어 사용될 수 있습니다.

### 1. 기술 스택 (Tech Stack)

| 구분 | 선택 기술 | 선정 사유 |
| --- | --- | --- |
| **Language** | **Java 21** | 최신 LTS 버전으로 Record, Virtual Threads, Pattern Matching 등 강력하고 간결한 문법 활용 가능 |
| **Framework** | **Spring Boot 3.x** | 의존성 주입(DI), 설정 관리의 편리함 제공. `CommandLineRunner`를 활용하여 CLI 환경 구성에 매우 적합 |

### 2. 시스템 아키텍처 (Architecture)

시스템은 '입력 데이터의 불확실성을 감추지 않고 드러내며 근거를 추적한다'는 핵심 목표에 따라 파이프라인 형태로 구성됩니다.

#### 2.1 전체 데이터 흐름 (Data Flow)

1. **Generation (생성 단계)**: 설정 파일(Scenario JSON)과 Seed를 입력받아 가상의 원본 투자안 및 문서를 합성.
2. **Ingestion & Normalization (수집 및 정규화 단계)**: 다양한 구조의 원본 데이터를 읽어 시스템 공통의 `Canonical Model`로 매핑.
3. **Review & Simulation (심사 및 시뮬레이션 단계)**: 
   - **Rule Engine**: 명확한 수치 비교(예: LTV 상한 초과, 특정 필수 필드 누락) 수행.
   - **AI Engine (Gemini)**: 규칙으로 잡을 수 없는 뉘앙스, 여러 문서 간 모순된 서술 등을 분석.
4. **Audit & Reporting (감사 및 보고 단계)**: 처리된 이력, 신뢰도, What-if 시뮬레이션 결과 등을 최종 리포트(JSON/Markdown)로 출력.

#### 2.2 모듈별 핵심 기능

- **Data Generator (합성 데이터 생성기)**
  - **재현성 보장**: 고정된 Seed 값 주입 시 항상 동일한 비정형 문서 및 데이터를 산출.
  - **오류 주입(Error Injection)**: 의도적으로 누락, 단위 혼동(백분율 vs 소수점), 문서 간 모순되는 값(IM 문서와 재무모델의 LTV 불일치 등)을 생성.

- **Pipeline & Normalizer**
  - **Source Model**: 각 자산군(부동산, 인프라, PE 등)별로 다르게 들어온 원본(텍스트 조각, 메타데이터).
  - **정규화(Normalization)**: 원본을 읽어 `Canonical Model`로 변환하되, 단순히 값을 덮어쓰는 것이 아니라 값의 **출처(Lineage)**를 기록.

- **Review & What-if Engine**
  - **규칙(Rule)과 AI의 결합**: 
    - 기본 심사는 규칙 엔진이 담당하여 속도와 일관성 확보.
    - 규칙 엔진이 확신할 수 없거나 모순을 감지한 경우 Gemini API를 호출하여 추가 분석.
  - **안전한 실패 처리**: 데이터가 충돌하거나 AI 판단 근거가 부족할 경우 시스템이 임의로 값을 병합하지 않고 상태를 `REVIEW(사람의 검토 필요)`로 플래그 처리.
  - **What-if 기능**: 이자율, 매각가 등의 가정을 변경하고 재실행할 경우, 변경 전후의 산출물 차이(Diff)를 계산하여 제공.

### 3. 데이터 모델 설계 (Data Model)

현실적인 복잡성(데이터의 출처, 신뢰도, 변경 이력)을 다루기 위해 단순히 기본 타입(int, String)을 사용하지 않고 추적 가능한 래퍼(Wrapper) 클래스를 도입합니다.

#### 3.1 TraceableField<T> (이력 추적 필드)
모든 주요 심사 지표(예: LTV, 기대수익률, 현금흐름)는 아래와 같은 속성을 감싸는 `TraceableField`로 정의됩니다.
- `T value`: 실제 데이터 값
- `String source`: 데이터의 출처 (예: "투자제안서 v2", "Gemini 추론")
- `double confidence`: 신뢰도 (0.0 ~ 1.0)
- `boolean hasConflict`: 다른 출처의 데이터와 충돌 여부
- `List<History> lineage`: 이전 값 및 수정 이력을 담는 리스트

#### 3.2 Canonical Model (공통 모델 구조)
자산군별 차이를 수용하면서도 공통 심사를 적용하기 위한 계층적 모델입니다.
```java
// 예시 코드 구조 (Java 21 Record 활용)
public record InvestmentProposal(
    String id,
    AssetType assetType, // REAL_ESTATE, INFRA, PE 등
    TraceableField<Double> requestedAmount,
    TraceableField<Double> ltv,
    Map<String, TraceableField<Object>> assetSpecificRisks,
    ReviewStatus status // APPROVED, REJECTED, REVIEW_REQUIRED
) {}
```

### 4. 핵심 시나리오 및 설계 대응 방안

제시된 복잡성 문제를 시스템이 어떻게 해결할 것인지에 대한 정의입니다.

| 식별된 문제 (복잡성) | 설계 및 구현 대응 방안 |
| --- | --- |
| **같은 수치가 문서마다 다름** | 충돌 발생 시 시스템이 임의 병합하지 않음. 두 값을 모두 보존하고 `hasConflict=true` 및 `status=REVIEW_REQUIRED`로 설정. Gemini AI에 두 문장을 주고 "어느 것이 최신이거나 더 타당한지" 근거 분석 요청. |
| **AI 의견의 근거 부족** | Gemini API 프롬프트에 반드시 **원본 텍스트의 인용구(Quote)를 포함**하여 답변하도록 강제. 인용구가 없는 AI 의견은 신뢰도(confidence)를 낮게 부여. |
| **규칙·스키마 변경 시 이력 보존** | 입력 데이터와 평가에 사용된 Rule/Model의 버전을 함께 결합하여 Report 산출. 과거 버전 Rule 엔진 호출 인터페이스를 분리하여 재현성 보장. |
| **사람과 자동처리의 경계** | 확실한 규칙 통과 및 AI 신뢰도 90% 이상 시에만 '성공(Approved)' 처리. 그 외 모호한 모든 건은 격리 후 사용자 검토 대상으로 분류. |

## Ⅱ. 실제 업무 데이터의 특징

아래 내용은 문제의 경계가 아니라 출발점입니다. 지원자는 중요한 문제를 선택하고, 추가로 발견한 현실적 복잡성을 설계에 반영하십시오.

| 복잡성 | 실제 상황에서 나타나는 특징 |
| --- | --- |
| **자료의 비정형성** | 투자제안서, IM, 재무모델, 계약서, 이메일이 서로 다른 형식과 버전으로 들어오며 같은 수치가 문서마다 다를 수 있습니다. |
| **상품별 구조 차이** | 부동산의 임대차·LTV, 인프라의 장기계약, PE의 레버리지·Exit, 사모대출의 담보·약정처럼 위험요인이 상품마다 다릅니다. |
| **미래 가정과 불확실성** | 현금흐름·매각가·환율·금리는 확정값이 아니며, 기준·가중치·심사 의견도 시점과 위원회에 따라 바뀝니다. |
| **근거와 책임** | AI 의견은 원문 근거, 사용한 규칙·가정·모델 버전, 사람이 수정한 이력을 추적할 수 있어야 합니다. |
| **데이터 품질과 보안** | 누락값, 단위 혼재, 음수·백분율 표현 차이, 민감정보, 스캔 품질 저하와 AI 환각을 함께 다뤄야 합니다. |

## Ⅲ. 과제 목표 — 창의적 도구 제작

심사 담당자가 문서를 넣으면 답이 나오는 블랙박스가 아니라, 투자안의 불확실성과 충돌을 발견하고 근거를 추적하며 가정을 바꿔 볼 수 있는 심사 지원 도구를 설계·구현하십시오.

### 1. 필수 능력

| No | 도구 능력 | 요구 내용 |
| --- | --- | --- |
| **C-01** | 시나리오·문서 생성기 | 최소 5개 자산유형의 투자안과 문서 조각을 생성합니다. 누락·단위 오류·문서 간 모순·비현실적 가정 등을 설정으로 주입하고 seed로 재현합니다. |
| **C-02** | 수집·정규화·근거 추적 | 서로 다른 구조의 입력을 공통 모델로 정규화하고, 값마다 출처·신뢰도·충돌 여부를 기록합니다. |
| **C-03** | 심사·What-if 도구 | 규칙과 AI를 결합해 위험·추가질문·판정 근거를 제시하고, 가정 변경 전후의 결과 차이를 설명합니다. |
| **C-04** | 품질·감사 리포트 | 누락·충돌·미확인 가정·AI 검증 실패를 확인하고, 재심사해도 이전 버전을 보존합니다. |

### 2. 데이터 규모와 재현성
- **규모**: 투자안 30건 이상, 자산유형 5종 이상, 문서 조각 100개 이상, 의도적 품질 문제 15종 이상을 생성하십시오. 모든 수치는 가상이어야 합니다.
- **제어**: 데이터 생성 조건과 오류 주입 비율을 설정으로 바꿀 수 있어야 합니다.
- **재현성**: 같은 seed와 설정으로 동일한 데이터를 다시 만들 수 있어야 합니다.
- **설명**: 생성 데이터가 왜 현실적이며 어떤 역량을 검증하는지 시나리오 카탈로그로 설명해야 합니다.

## Ⅳ. 지원자가 스스로 정의할 사항

다음 항목에는 하나의 정답이 없습니다. 선택한 답보다 대안을 비교하고 근거와 한계를 설명하는 능력을 평가합니다.

| 설계 질문 | 고려 사항 |
| --- | --- |
| **반드시 남길 증거** | 누가 이 도구를 언제 사용하는가 (사용자, 의사결정, 성공·실패 기준) |
| **무엇을 같은 데이터·다른 데이터로 볼 것인가** | 키·불변조건·시간 기준·허용오차 |
| **자동처리와 사람 검토의 경계는 어디인가** | 임계값, 보수적 실패, 수동 결정과 이력 |
| **데이터가 틀렸을 때 어떻게 안전하게 실패하는가** | 오류 분류, 격리, 재처리, 부분 성공 정책 |
| **규칙·스키마·AI 모델이 바뀌면 무엇을 보존하는가** | 버전, lineage, 재현성, 변경 전략 |
| **마감까지 무엇을 하지 않을 것인가** | 제외 범위와 이후 확장 계획 |

## Ⅴ. 구현 범위와 완료 조건

### 1. 최소 완료 조건
- 한 줄 명령으로 데이터 생성부터 분석·처리·검증 결과 생성까지 재현됩니다.
- 지원자가 정의한 핵심 시나리오 10개 이상이 실제로 동작하며 정상·경계·오류가 구분됩니다.
- 오류나 불확실성을 무시하지 않고 원본 식별자·판단 근거·처리 상태를 남깁니다.
- 설계 문서, 코드, 실행 결과와 테스트가 서로 일치합니다.

### 2. 심화 요구사항 (선택 · 가점 5점)

*(평가자는 README의 실행 명령을 그대로 입력합니다. 명령이 동작하지 않으면 별도로 문의하지 않고 '실행 불가'로 처리합니다.)*

| 항목 | 내용 |

## Ⅸ. 유의사항

2. **AI 활용에 대한 입장**: 당사는 실무에서 AI 도구를 적극 활용합니다. AI 사용은 전혀 제한하지 않습니다. 다만 AI가 만들어 준 결과를 이해하지 못한 채 제출하는 것과, 이해하고 검증한 뒤 제출하는 것은 명확히 구분하여 평가합니다. 대화 전체를 제출할 필요는 없으나 핵심 판단의 증거는 남겨야 합니다.
3. **조사와 출처**: 외부 자료 조사는 허용합니다. 공개 표준·문서·오픈소스를 참고했다면 링크와 활용 범위를 명시하십시오. 업무 도메인에 대한 사실을 단정할 때는 근거와 가정의 경계를 구분하십시오.
4. **보안**: 실제 고객 데이터, 개인정보, 회사 기밀, 유료 API 키를 제출물에 포함하지 마십시오. 직접 생성하는 데이터는 모두 가상이어야 합니다.
5. **구두 리뷰**: 면접 시 제출물의 특정 부분을 지목해 설명을 요청드립니다. 본인이 작성한 코드와 문서의 내용을 설명할 수 있어야 합니다.
6. **표절 및 대리 작성**: 공개된 소스코드나 타인의 산출물을 출처 표기 없이 제출한 사실이 확인되면 전형에서 제외됩니다. 참고한 자료가 있다면 SUBMISSION.md에 출처를 밝히십시오. 출처를 밝힌 참고는 감점 사유가 아닙니다.
7. **정직한 범위 관리**: 마감까지 모든 문제를 해결할 필요는 없습니다. 중요한 문제를 선택한 이유, 해결하지 않은 문제와 위험, 다음 단계가 명확하면 좋은 평가를 받을 수 있습니다.
